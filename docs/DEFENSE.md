# Что показать на защите

1. Откройте магазин через кнопку бота и кабинет через аккаунт из MANAGER_IDS. В «Склад» оформите поступление 10. Начальный остаток автоматически не придумывается.
2. Соберите шаурму с халапеньо и без майонеза. Покажите изменение цены, отдельные рецепты в корзине, сумму заказа и серверный таймер 120 секунд.
3. До оплаты в кабинете: 10 / 1 / 9. После учебной оплаты: 9 / 0 / 9; одна продажа в журнале. Выручка и себестоимость добавки включены в финансы. Переключение «Выдан» второй раз склад не списывает.
4. Откройте полный возврат. Только подтверждение провайдера возвращает товар и сторнирует себестоимость. Если провайдер недоступен, видны ожидающее задание, число попыток и причина.
5. Запустите `python -m tests.acceptance --rounds 5 --buyers 20 --stock 1`. Покажите разделы 2, 3, 8–12 отчёта. Это реальные HTTP-запросы к двум процессам с одной SQLite; общий барьер запуска, а не последовательный цикл.
6. В разделе 9 отчёта: А освободил последнюю единицу, Б купил её, после этого пришла оплата А. У Б остаётся продажа, у А — конфликт и денежный возврат. Поступления 2400 ₽, возврат 1200 ₽, поток 1200 ₽, себестоимость 700 ₽, результат 500 ₽. Склад 0 / 0 / 0.
7. Раздел 10 действительно останавливает сервер с резервом и запускает после срока; раздел 11 останавливает его после commit поздней оплаты, затем моделирует отказ и потерянный успешный ответ провайдера. Раздел 12 завершает процесс через `os._exit` внутри незавершённой транзакции. Проверки читают базу после восстановления.

## Что объяснить своими словами

- `BEGIN IMMEDIATE` получает право записи до чтения доступности; второй процесс ждёт. Обновление, заказ, позиции, резерв, ключ повтора и журнал коммитятся вместе. При ошибке ничего из этого не остаётся.
- Ключ покупки не равен ID пользователя: у одного пользователя могут быть разные покупки. Повтор ключа возвращает старый заказ; другой состав с тем же ключом — конфликт.
- Таймер клиента декоративный. Оплата проверяет серверное время уже внутри транзакции. При равенстве срок истёк.
- Освободить можно только active; продать — только active и до срока. Эти проверки выполняются после получения блокировки базы. Повтор не проходит тот же переход второй раз.
- Деньги и склад не одно и то же. Поздняя оплата — факт получения денег, но товар не продавался. Поэтому её возврат не прибавляет товар и не сторнирует себестоимость.
- Успешный платёж не откатывается поздним canceled. При любой повторной оплате проверяется исходная сумма и валюта.
- Задание возврата — долговечная запись; попытка обращения к провайдеру — отдельное действие. Потерянный ответ проверяется по постоянному ключу. Поле attempts считает попытки обработки, а не число денежных возвратов.

## Использование AI и исправления

Весь код этого этапа подготовлен с помощью Codex. Формулировки ниже — краткая запись задач и уточнений по выполненной работе, а не выдуманная дословная переписка с несколькими людьми.

Основная задача: «Доработать существующий магазин на aiogram/aiohttp/SQLite: картинки, рецепты, склад, 120-секундные резервы, гонки, поздние платежи, восстановление и фактические проверки».

Уточнение 1: «Сохранить существующие таблицы и снимки себестоимости. Старые продажи не списывать с нового склада. Начальные количества проводить только поступлением».

Уточнение 2: «Не подтверждать возврат вручную из браузера. Сохранять задание, обращаться к имитатору вне транзакции и моделировать потерянный успешный ответ».

Исправление 3: «Windows оставляет тестовую базу занятой после остановки. Закрыть все SQLite-соединения и завершать настоящий процесс сервера, затем повторить тот же тест». Полный протокол — reports/FIRST_FAILURE.md.

Второе уточнение к тестам: управляемые часы нужно продвигать и для повторов возврата, иначе `next_attempt` никогда не наступит. В проверке явно проходят время первой ошибки, потери ответа и следующей попытки. В обычном запуске часы системные и идут сами.

## Запись демонстрации

`screenshots/` содержит фактические кадры браузерной проверки на отдельной вымышленной базе. Это демонстрация интерфейса; доказательства конкуренции и принудительных остановок — в машинном отчёте, а не в картинках.

`demo.gif` — 39-секундная пошаговая демонстрация, собранная из фактических кадров: меню → конструктор → резерв → оплата → склад → финансы → последняя единица для А и Б → поздняя оплата А с возвратом → итог 500 ₽ → остановка и восстановление резерва. Это анимация кадров, а не непрерывная видеозапись экрана.

Последняя часть снята на отдельном вымышленном товаре №7: 1200 ₽ / 700 ₽ / одна единица. Все действия заказа, поступления и платежа проведены через настоящий API с учебными подписанными личностями; записи сохранены в DEMO_LOG.json. Для перезапуска HTTP-сервер действительно остановлен, управляемое время продвинуто на 120 секунд при остановленном сервере, затем запущен тот же процесс с той же базой. После запуска 1 / 1 / 0 стало 1 / 0 / 1. Автотесты повторяют эти правила без зависимости от демонстрационных кадров.

Бот и ЮKassa с вашим настоящим Telegram-аккаунтом здесь не запускались; для их проверки нужны ваша конфигурация и публичный HTTPS-адрес. Ни токены, ни персональная база в пакет не включены.
