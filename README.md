# Шаурма на углу

Учебный проект по веб-разработке. Три практические работы развивают один магазин на Telegram, aiohttp и SQLite.

| Работа | Что можно показать |
| --- | --- |
| 1. Telegram-магазин | Каталог, корзина, оформление заказа и управление статусами в боте. |
| 2. Финансовый кабинет | Оплаты, возвраты, расходы, себестоимость и журнал операций. |
| 3. Mini App и склад | Витрина, конструктор рецепта, резервы на 120 секунд, конкурентные заказы и обработка поздних платежей. |

[Демо-витрина](https://cosider24.github.io/shawarma-bot/) показывает учебный каталог, конструктор и корзину. Для оформления заказов, оплаты и кабинета менеджера запустите Python-сервер и откройте Mini App из Telegram.

[Сценарий защиты](docs/DEFENSE.md) · [Скриншоты](docs/screenshots/) · [Отчёт о приёмке](reports/acceptance.md)

## Правила распродажи (зафиксированы до реализации)

Менеджер открывает «Кабинет → Склад», оформляет поступление с уникальным ключом и видит три остатка: на складе / в резерве / доступно. Добавление в корзину не резервирует товар. Оформление всего заказа резервирует его на 120 секунд. Если хотя бы одной позиции не хватает, вся транзакция откатывается.

SQLite `BEGIN IMMEDIATE` сериализует записи разных процессов; все позиции изменяются в порядке ID. Успешная оплата до срока потребляет резерв. Отмена и истечение освобождают его только один раз. При `now >= expires_at` оплата поздняя даже при задержке фоновой задачи. Побеждает первый допустимый переход в транзакции; нельзя отменить принятую продажу без возврата.

Поздняя оплата фиксируется как деньги, заказ получает `payment_conflict`, а постоянное задание полного возврата сохраняется в той же транзакции. Чужой товар не забирается. Поздний возврат не увеличивает склад и не признаёт себестоимость. Обычный подтверждённый возврат продажи возвращает товар и себестоимость один раз. До подтверждения финансовый результат и товар не меняются.

Резервы и задания возврата сохраняются в общей базе. При запуске и каждые 5 секунд работник освобождает сроки и продолжает возвраты. Внешние запросы не держат транзакцию SQLite. Повтор использует постоянный ключ, после потерянного ответа сначала проверяется состояние провайдера.

## Что добавлено

- Покупательская Mini App `/shop`: адаптивная витрина, шесть собственных локальных иллюстраций, категории, конструктор, независимые варианты одного блюда, количества и комментарий кухне.
- Добавки: халапеньо +30 ₽, двойной сыр +40 ₽, дополнительная начинка +70 ₽, грибы +40 ₽. Можно убрать ингредиенты, в том числе майонез у классической. Удаление ингредиента бесплатно и не снижает цену; себестоимость базового рецепта сохраняется консервативно, стоимость добавок увеличивает её. Цены и рецепты определяет сервер. Составы — учебные, предупреждение об аллергенах не заменяет сведения реальной кухни.
- Корзина хранится на устройстве; Telegram-корзина прежнего бота остаётся серверной. Они используют один каталог, общую базу, одинаковое оформление, склад, платежи и журнал. Они не синхронизируются между собой: нестандартные рецепты теперь можно собрать и в боте, и в Mini App. Telegram-корзина сохраняет варианты в bot_cart_lines.
- Бот: изображения товаров, доступное количество, открытие магазина, остаток времени и безопасная отмена. Успешная учебная оплата проходит через тот же обработчик, что Telegram successful_payment.
- Кабинет `/`: прежние сводка, расходы и финансовый журнал; новые поступления, три остатка, резервы, движения, ошибки возвратов, отмена неоплаченного заказа, этапы приготовления оплаченного заказа.
- Фоновые возвраты с постоянным ключом и повтором, арендой задания между процессами и уведомлением после подтверждения. Имитатор умеет временную ошибку и потерю успешного ответа.
- Изолированные автоматические сценарии с двумя процессами сервера, подписанными вымышленными покупателями и проверкой реальной SQLite.

## Быстрый запуск на Windows

Нужен Python 3.12 или новее. Распакуйте проект в отдельную папку, откройте в ней PowerShell:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Заполните `.env`: ваш `BOT_TOKEN`, ваш числовой Telegram ID в `MANAGER_IDS` (команда `/id` в боте показывает ID), `PAYMENT_MODE=simulator`. Оставьте `SHOP_TEST_MODE=0`. Для первого локального запуска `WEBAPP_URL` можно пока не задавать.

```powershell
.\.venv\Scripts\python.exe manage.py init
.\.venv\Scripts\python.exe manage.py seed-demo
.\.venv\Scripts\python.exe bot.py
```

`seed-demo` — явные учебные поступления по 10 единиц. Повтор не удваивает их благодаря постоянным ключам. На существующем складе вместо этой команды оформляйте нужные количества через кабинет. Инициализация сама запасы не добавляет.

Общий сервер работает на `http://127.0.0.1:8080`. Предоставьте ему публичный HTTPS через уже использованный вами туннель или свой хостинг. Укажите его **корень** в `WEBAPP_URL` без `/shop` и перезапустите бота. В BotFather разрешите этот домен для вашего бота. Покупательская кнопка откроет `/shop`, менеджерская — `/`.

Отдельный HTTP-сервер для диагностики: `python server.py` (без Telegram polling; создание счёта ЮKassa через Telegram в этом режиме недоступно). Не запускайте его на том же порту одновременно с `bot.py`. Работник уже встроен в оба способа запуска, отдельная очередь не нужна.

После первоначальной настройки можно запускать `./start.ps1`: скрипт устанавливает зависимости и запускает бота из правильной папки. Если PowerShell ограничивает запуск скриптов, используйте команды выше; менять системные настройки для проекта не требуется.

### Сохранение старого магазина

Исходный ZIP и ваша база не изменялись. В этом пакете нет `.env`, реальной `shop.db`, старой `.git` и чужого виртуального окружения.

1. Остановите старый бот и сделайте резервную копию своей базы штатным способом (для остановленной SQLite достаточно копии файла).
2. Перенесите в новую папку **свои** `.env` и `shop.db` либо задайте абсолютный `SHOP_DB` в `.env`.
3. Запустите `python manage.py init`. Миграция добавляет таблицы/колонки и повторно безопасна. Исторические orders, order_items, payments, finance_operations сохраняются; оплаченные заказы не резервируются и товар по ним повторно не списывается. Отчёты по ним продолжают учитывать прежние снимки себестоимости.
4. Явно оформите начальное поступление. После этого запускайте новый бот. Не держите старую версию одновременно: она не знает правил склада.

## Схема и согласованность

Сохранены прежние таблицы. Добавлены `stock`, `reservations`, `reservation_items`, `stock_journal`, `checkout_requests`, `refund_jobs`, `simulator_refunds`, `simulator_faults`. В `orders` добавлены признаки принятой продажи и управления складом, в позициях — ID товара и JSON рецепта.

Связь: product → reservation_items → reservation → order → payment → finance_operation; refund_job ссылается на payment. Остатки целые, ограничения SQLite проверяют `on_hand >= 0`, `reserved >= 0`, `reserved <= on_hand`. Состав резерва агрегируется по товару, даже если в заказе несколько разных рецептов этого товара.

Запись использует `BEGIN IMMEDIATE` и ожидание блокировки до 15 секунд. Каждый запрос/попытка работника получает независимое соединение. При нехватке — 409; при исчерпании ожидания SQLite — 503 с предложением повторить прежний ключ. Это техническая ошибка, не штатный отказ по наличию. Все движения проходят сервер и имеют уникальный ключ журнала. История не удаляется.

У резерва состояния `active → consumed` или `active → released`. Отдельно заказ: `awaiting_payment → paid / canceled / expired / payment_conflict`. Поле status хранит прежние русские этапы кухни. Платёж: `pending / canceled → succeeded → refund_pending → refunded`; запоздалый canceled меняет только pending. У задания возврата собственные `refund_pending → refund_succeeded`. Это соответствует подтверждённому полному возврату, хотя старое название платежа `refunded` сохранено для совместимости.

У нового заказа один платёж: повтор открытия счёта возвращает его же, дополнительная вставка защищена триггером БД. Старые исторические попытки оплаты не удаляются. Ключ оформления уникален в паре с покупателем; отпечаток включает позиции, их количества, варианты, имя, получение и комментарий. Изменение каталога не меняет результат уже сохранённого повтора. При явном отказе по нехватке нового заказа/резерва нет; после исправления корзины Mini App создаёт новый ключ. При сетевой ошибке запрос и ключ сохраняются до безопасного повтора.

Срок — UTC epoch с дробными секундами, без округления на границе. Платёж после срока признаётся поздним, даже если покупатель нажал кнопку раньше. Просроченные резервы освобождаются при старте и каждые `WORKER_INTERVAL` секунд. `RESERVATION_SECONDS` по умолчанию 120, интервал 5. Клиентский таймер использует разницу с server_time и не меняет склад.

### Формулы финансов

Деньги — целые копейки. Базовые цены каталога и позиции прежнего проекта — целые рубли; сервер переводит итог в копейки для платежа.

Денежный поток = поступления − подтверждённые возвраты − действующие расходы.

Учебный результат = поступления − возвраты − себестоимость принятых продаж + себестоимость возвращённых принятых продаж − расходы.

Поздние деньги до возврата временно увеличивают поток и результат, но себестоимость у них нулевая. После возврата этот эффект исчезает. У принятой продажи себестоимость и цена — снимки на момент оформления, включая добавки. Журнал денег хранится по UTC, фильтры периода относятся к этим календарным датам.

### Восстановление возврата

Обработчик оплаты атомарно сохраняет деньги и задание. Работник короткой транзакцией получает аренду задания на 30 секунд; внешнее обращение выполняет снаружи транзакции. Другой процесс не обрабатывает арендованное задание. После аварии аренда истечёт, задание продолжится. Ошибка сохраняет текст и next_attempt, деньги до подтверждения не считаются возвращёнными.

Имитатор сохраняет своё подтверждение в отдельной таблице до ответа магазину. После потерянного ответа работник сначала читает подтверждение по постоянному ключу и завершает одну операцию. Это учебная модель внешнего провайдера в той же SQLite; она сохраняет независимые commit провайдера и магазина, но не имитирует отдельный сетевой сервис.

Для ЮKassa сохранены тестовые Telegram invoices и API возврата. Используйте **тестовый** PROVIDER_TOKEN (с `:TEST:`), YK_SHOP_ID и YK_SECRET_KEY. Конфигурация отклоняет live provider token. Подтверждение оплаты приходит через Telegram successful_payment с проверкой владельца, сохранённой суммы и валюты; браузер в режиме yookassa сам оплату не подтверждает. Повтор возврата использует постоянный UUID в Idempotence-Key; известный refund_id проверяется через GET. Проверяются также принадлежность возврата платежу, полная сумма и валюта ответа. Интеграция с внешней ЮKassa в этой сессии **не запускалась**, нужен отдельный тест вашего тестового магазина.

ЮKassa хранит идемпотентность [24 часа](https://yookassa.ru/developers/using-api/interaction-format#idempotence). Если refund_id неизвестен, после 23 часов от первой попытки автоматический POST прекращается: остаётся видимая ошибка со сверкой у провайдера. Для старых refund_pending миграция сохраняет прежний ключ `refund-ID`; при неизвестном времени прошлой попытки внешний POST также блокируется. После сверки администратор восстанавливает проверенный refund_id в серверной базе, и работник продолжает GET-проверку. Старые успешные платежи и завершённые возвраты не отправляются заново.

## Авторизация и API

Каждый `/api/` запрос проверяет подпись Telegram initData и auth_date, повторяющиеся поля отклоняются. Покупательские пути `/api/shop/` проверяют владельца заказа/платежа. Остальные API доступны только MANAGER_IDS на каждом запросе. Цена, себестоимость, срок и роль из браузера не принимаются. В учебном simulator покупатель может подтвердить только собственный учебный платёж без передачи произвольной суммы.

Основные пути:

- `/api/shop/me`, `/api/shop/catalog`, `/api/shop/orders`, `/api/shop/orders/{id}` — покупательские данные.
- POST `/api/shop/checkout` — items, name, delivery, note, request_key; в позиции только product_id, qty, add, remove.
- POST `/api/shop/orders/{id}/pay`, `/cancel`; `/api/shop/payments/{id}/simulate` — учебный результат своего платежа.
- `/api/stock` — три остатка, резервы, последние 300 движений и 200 возвратов; POST `/api/stock/receive` — product_id, qty, request_key.
- POST `/api/orders/{id}/refund`, `/refund/finish`, `/cancel`, `/status` — действия менеджера. Проверка возврата обращается к работнику, браузер не назначает успешный результат.
- POST `/api/stock/sweep` — менеджерская немедленная проверка сроков и заданий; используется также для конкурентной приёмки.
- Прежние `/api/summary`, `/api/journal`, `/api/expenses` сохранены.

База содержит полный журнал; интерфейс ограничивает объём последних записей. Для архивного расследования используйте SQL или выгрузку из SQLite. В этом учебном этапе нет доставки с адресами, скидок, реальных денег, складского учёта отдельных ингредиентов и частичных возвратов. Запасы учитываются по готовому товару; добавки влияют на цену, себестоимость и состав. Аллергены и вес в каталоге требуют замены данными настоящей кухни перед коммерческим использованием.

## Воспроизводимая приёмка одной командой

```powershell
.\.venv\Scripts\python.exe -m tests.acceptance --rounds 5 --buyers 20 --stock 1 --reserve-seconds 120
```

Команда сама создаёт схему, вымышленный каталог (товар №1: цена 1200 ₽, себестоимость 700 ₽), начальные поступления, подписи тестовых покупателей, две HTTP-службы и **отдельную временную базу для каждого сценария/повтора**. Она не читает исходную shop.db, не подставляет настоящие токены и не требует работающего бота. После проверки останавливает принадлежащие ей процессы и удаляет только созданные временные каталоги. Удалять или сбрасывать ваш магазин для тестов не нужно.

Параметры `--buyers`, `--stock`, `--reserve-seconds` меняют дополнительный сценарий конкуренции и длительность резервов. Обязательные 1/20 и 10/50 также всегда выполняются; минимум пять повторов. Для конкуренции клиенты ждут общий `threading.Barrier` и обращаются к настоящему HTTP через разные процессы. Срок в тестах контролируется файлом часов, недоступным по API. На границе времени проверяются отдельные исходы, а гонки сохраняют фактического победителя в отчёте.

Проверки читают ответы и SQLite: orders, reservation_items, payments, journal, суммы финансов, CHECK/UNIQUE, foreign_key_check и integrity_check. Задания возврата проходят реальные методы имитатора, включая ошибку и потерю ответа. Аварии до commit и после записи позднего платежа — действительное завершение процесса, а не ручная правка состояния в таблице.

Результат — `reports/acceptance.md` (сценарий → ожидалось → получено) и подробный `reports/acceptance.json` с ID, журналом и финансовыми записями. При провале код завершения ненулевой и traceback сохраняется. `--report путь.json` позволяет сохранить новый прогон отдельно. Часы повтора возврата в тестах тоже явно продвигаются, иначе next_attempt при остановленном времени не наступил бы.

Регрессия финансов и миграции предыдущего этапа:

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_scenarios -v
.\.venv\Scripts\python.exe -m unittest tests.test_provider -v
```

Сценарии прежнего этапа обновлены под новые правила: явное поступление в подготовке, один счёт на заказ, достоверный success после canceled учитывает деньги, повтор возврата безопасен, подтверждение делает работник.

`tests.test_provider` — четыре локальные проверки контракта ответа ЮKassa с имитацией ответа, включая несовпадающие реквизиты и окно идемпотентности. Это не подтверждение работы с внешним платёжным аккаунтом.

Точки аварии (`SHOP_FAILPOINT=checkout_before_commit` и `after_late_payment`) работают **только** при `SHOP_TEST_MODE=1`. Их выставляет тестовый стенд, публичных HTTP-кнопок остановки/изменения часов нет. Обычный запуск держите в режиме 0. Набор можно повторять без специальной команды сброса: каждый прогон сам создаёт новую тестовую базу.

Для добавления новых позиций дополните серверные `INGREDIENTS` и `product_meta` в stock.py; готовые шесть товаров используют исходные ID каталога.

Исходные технические правила сверены с [транзакциями SQLite](https://www.sqlite.org/lang_transaction.html) и [проверкой Telegram initData](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).


## Обновление Telegram и запуска

Состав настраивается прямо в боте. Картинки и экраны редактируются в одной панели. Запуск bot.py автоматически включает HTTPS-туннель через установленный cloudflared и обновляет адрес в .env. Старые открытые окна Mini App нужно закрыть и открыть новой кнопкой после /start. Для своего постоянного туннеля задайте AUTO_TUNNEL=0. Подробности и фактические проверки — reports/BOT_FIX.md.
